# Asset Catalog Phase — plan

**Headline**: The bottleneck has shifted from *can we render the original
frames* to *can we identify and describe every asset well enough that the
engine can pick the right model/texture for each situation.*

We have ~thousands of assets across textures, sprites, meshes, animations,
icons, inventory, audio, and effects. Each needs structured metadata:
original location (which OMT file, which chunk), usage function (what role
does it play in gameplay), animation flags (is it moving? rigged?
billboard?), relative scale, screenshots from real gameplay, and free-form
description. Without that, no programmatic system — engine, AI selector,
human contributor — can reliably resolve "the brown thing in front of
Jimmy" to `RampsNEW02`.

This plan covers the next major work block. It bundles awefan4524's
contribution starters (P1 + P2 from `CONTRIBUTING_AWEFAN.md`) because they
have material overlap, and re-scopes them for a wider audience.

## Audience (in scope)

This system is being built for at least three classes of user:

1. **Maintainers** (Scotty, awefan) — Linux + Python literate, comfortable
   with CLI, will hand-edit catalog entries when needed.
2. **Tech-comfortable contributors** — may be on Windows or macOS, can
   install Python, can run a desktop app, but should never need to touch
   Docker, CI, or git internals to be useful.
3. **Domain contributors with low tech literacy** — fans of the original
   game who know what a "Yokian saucer" looks like and can write a one-line
   description, but who can't be expected to install Python at all.

Audience 3 is the surprising one and it shapes the architecture:

- The browser must run on Windows / macOS / Linux out of one source tree
  (Qt does this; PyInstaller will produce portable bundles for the first
  two; Linux gets a native build, no `omt.exe` dependency).
- The catalog must be *readable* and *editable* without the GUI — the
  markdown table in `docs/asset-catalog.md` is the human source of truth.
  A contributor without Python should be able to fork, edit the markdown,
  and open a PR.
- The GUI should produce screenshots and thumbnails automatically so
  contributors don't need to know how to take them.

## What the catalog must capture (schema)

Per asset:

| field | required | source |
|---|---|---|
| `key` | yes | `<container>/<chunk-type>/<chunk-id>/<chunk-name>` |
| `kind` | yes | `texture`, `sprite`, `mesh`, `animation`, `icon`, `audio`, `effect`, `inventory` |
| `name` | yes | from named-chunk table (fallback: `type_id`) |
| `origin.file` | yes | e.g. `assets/omt/level1.omt` |
| `origin.chunk_id` | yes | numeric chunk id |
| `origin.byte_offset` | yes | absolute file offset |
| `origin.size_bytes` | yes | from chunk table |
| `dimensions` | when applicable | `{w,h}` for textures, `{verts,polys,bbox:{min,max}}` for meshes |
| `animation.is_animated` | yes | bool — does it move at runtime |
| `animation.frame_count` | when animated | number of frames |
| `animation.billboard` | when applicable | `none`, `y-axis`, `full` |
| `relative_scale` | yes | rough size class: `prop` (≤1m), `small` (1–3m), `mid` (3–10m), `large` (10m+), `landscape` |
| `usage.function` | yes | one of an enum: `building`, `terrain`, `vegetation`, `prop`, `npc`, `player`, `ui`, `vfx`, `transport`, `interactive`, `collectible`, `decor` |
| `usage.notes` | optional | free-form sentence |
| `screenshots` | optional | list of paths (autogenerated previews + gameplay captures) |
| `counterparts` | optional | linked keys — e.g. a tree mesh links to its leaf billboard sprite |
| `description` | yes | one or two sentences in plain English (this is what the AI selector reads) |
| `status` | yes | `unannotated`, `auto-filled`, `human-reviewed`, `verified-in-game` |
| `xp_notes` | optional | bytes-level observations, capture frame references |

The JSON sidecar holds this at runtime; `docs/asset-catalog.md` mirrors it
as a sortable markdown table for human review. The two are kept in sync by
a `catalog sync` subcommand of the CLI.

automation and a Qt desktop app for the human workflow. Both wrap a thin
core library so there's one place for OMT parsing logic.

the catalog schema, the markdown bridge, the autofill heuristics, the
thumbnail pipeline, and the cross-platform packaging.

## Overhaul concerns (real, from feedback)

### Mesh data shape: n-gons vs triangle buffers

Their `OMTMesh` exposes polygons as `List[Dict]` where each polygon owns
`v_idx`, `n_idx`, `uv`, `normal`. Pros: matches the OMT serialization
verbatim. Cons:

- Modern GL/Vulkan pipelines want a flat `(N, 3)` index buffer with
  per-vertex (not per-corner) UVs.
- UVs are per-corner in OMT, so the same vertex position appears with
  different UV values at different polygons. A triangle-buffer view has
  to "split" vertices: duplicate positions where UVs differ.

Empirically across level1.omt: **5,255 of 5,255 polygons are already
triangles**. So the n-gon code path isn't exercised by this game's
authored data — but the *shape* still bites us at the rendering stage.

The toolkit's `core/mesh.py` adds:

```python
@dataclass
class TriangleBuffer:
    positions: np.ndarray  # (V, 3) f32, vertices split by UV
    uvs: np.ndarray        # (V, 2) f32
    normals: np.ndarray    # (V, 3) f32
    indices: np.ndarray    # (N, 3) u32
    material_per_tri: np.ndarray  # (N,) u32, index into materials table

def to_triangle_buffer(mesh: OMTMesh) -> TriangleBuffer: ...
```

This is the bridge layer. Their parser stays untouched (n-gon preserving
for fidelity); ours adds the engine-friendly view. We send this back to
awefan as a contribution to `omt-3D-lib` once it's stable.

### v3+ extra-pass texture sets — what they are, why they matter

In 3DSP shape **version 5**, each polygon can carry an additional integer
`text_extra_index` that points into the mesh's `extra_textures` table.
Each entry in that table is a "pass set" — a list of additional texture
*passes* to apply on top of the base material:

```
extra_textures: List[PassSet]
PassSet = List[Pass]
Pass = (stream_link, texture_address_mode, color_op)
       stream_link is a (lt, li) tuple — the chunk type + id of the
                   Canvas to bind
       texture_address_mode = wrap / clamp / mirror (D3D enum)
       color_op             = how this pass combines with the previous
                              (D3D7 multi-texture stage state)
```

This is how D3D7 multi-texturing was authored: stack up to a few texture
stages per polygon for things like base-color × lightmap × detail-noise.
PS1/PS2/Dreamcast-era pipeline.

**Why we haven't hit it**: level1.omt and level3d.omt are entirely 3DSP
version 2 — no `extra_textures` at all. Their parser handles v5
correctly on paper but has no test fixture. We can solve this for awefan
in two ways:

1. **Synthetic fixture** — hand-write a tiny v5 3DSP block in Python:
   ```python
   # 1 vertex, 1 triangle, 1 extra-pass-set with 2 passes
   #   pack header, version=5, spheres, vcount=3, polygons=1 with
   #   nverts=3 + v3+ layout + flags + text_extra_index=0,
   #   then a single extra-pass-set with two (slink, am, co) entries.
   ```
   This validates `parse_3dsh_bytes` produces correct counts and types
   without needing a v5 game.

2. **Find a real v5 sample** — other AWE Games titles (Bratz Rock Angelz,
   Agatha Christie) may ship at higher versions. awefan has worked on
   these; they may already have one on disk.

We can ship (1) as a regression test in the toolkit and ask awefan to
contribute (2) when convenient. That removes the open-question status of
their v5 code.

## Decisions to make before starting

1. **Repo home for the toolkit**: dedicated `omt_asset_toolkit` (my

   changes get expensive.

   in jn-engine. After M2, does it live in jn-engine (and the toolkit
   syncs against it via a path arg) or in the toolkit repo (with
   jn-engine consuming it)? My vote: stays in jn-engine; the toolkit is
   a tool not a data store.

## Thumbnail / preview rendering — UV artifact diagnosis

The naive software rasterizer used in the POC scripts (`render_hydrant.py`,
`compare_hydrant_capture_vs_native.py`) produces visible sampling
artifacts on tiled-UV objects like the firehydrant: the texture's
internal detail (bolt heads, horizontal stripes) doesn't surface on the
rendered face. This is *not* a convention bug and *not* per-object.
We've already triangulated it to a rasterizer-level issue:

- **Convention is fine.** OMT 3DSP UVs are D3D-convention (V=0 at top
  of texture). Canvas decoders (ours and awefan's) write rows
  top-to-bottom, so PIL pixel(0,0) is the top. Sampling with
  `y = int(v*(h-1))` requires no flip and is the correct mapping. The
  same UVs render the same artifact regardless of whether they came
  from the native OMT mesh or from the captured `DRAW_PRIMITIVE`
  vertex stream — confirming the data is consistent across both
  sources.

- **Not per-object.** The artifact appears on any mesh whose UVs lie
  largely outside `[0,1]` and rely on wrap mode, which is most of
  JNBG's environment art. Objects with UVs cleanly in `[0,1]` (sprites,
  HUD elements) don't show it.

- **Root cause.** Three rasterizer-level shortcomings, in increasing
  order of impact:
  1. Nearest-neighbor texture sampling (no bilinear), so adjacent
     pixels alias instead of blending.
  2. No mipmap selection — when one screen-space triangle covers many
     texels (small face, tiled UVs), every sample lands in the same
     few-texel region.
  3. Linear UV interpolation in screen space (we lerp `u` and `v` with
     barycentric weights), not perspective-correct (`u/w`, `v/w`,
     `1/w` lerped and then divided). At grazing angles this skews UV
     toward the near vertex.

The fix is to **stop hand-rasterizing**. M3 of this plan moves
thumbnail rendering into a real OpenGL context (Qt's `QOpenGLWidget` or
offscreen EGL for the CLI). Bilinear + trilinear mipmap filtering +
perspective-correct interpolation are all GL defaults; we get them for
free. There's no need to re-examine the raw capture stream to fix this
— we've already verified the same UVs from both the OMT mesh and the
captured draws produce identical artifacts under the current
rasterizer.

Per-mesh thumbnail rendering in `core/thumbs.py` should use an
offscreen FBO with these states:

```
glEnable(GL_DEPTH_TEST)
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_LINEAR_MIPMAP_LINEAR)
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_LINEAR)
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_S, GL_REPEAT)
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_T, GL_REPEAT)
glGenerateMipmap(GL_TEXTURE_2D)
```

That's the whole intervention. We can keep the software rasterizer for
debug visualization (it's useful for confirming UV byte layouts at
parse time), but it stops being the user-visible thumbnail path.
