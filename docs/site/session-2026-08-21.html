Session notes · 21 August 2026

Checks That Couldn't Fail

A day's work on the Jimmy Neutron reimplementation. The VR levels stop being dead ends and the start point picks the right cutscene again — and then, looking for the next thing to port, three of the project's own mutation tests turn out never to have run the code they claimed to mutate.

What you can play

All of this is in the QA5 Windows build, linked at the bottom.

Fixed

The VR levels are no longer dead ends

Every VR level has a portal that takes you back out. All ten of them, across VR01–VR08, author the destination RETURN — meaning go back where you came from — and the engine took that literally: it asked for a level named "RETURN", failed to find one, and left you stuck.

They work now. How you got in matters: enter a VR level through the in-game menu and the portal returns you to the level the menu left from. Jump straight to one from the launcher and there is nothing to go back to — so the portal says so in the console, rather than silently doing nothing.

Fixed

The start point picks the cutscene

On a new game, the spot you arrive at now decides which scene plays. The engine used to play every standalone camera shot in the level, one after another, as a single "intro" — fourteen of them in level 1 — and never touched the multi-shot sequences at all, which is where the real scripted scenes live.

The level data was unambiguous once we looked: of the 100 start points in the game, 31 name something, and 22 of those name a camera. Every VR level's start point names its own briefing. Level 1e has four entrances and each one names a different scene.

Was wrong

Two portals doing the wrong thing

One portal in level 4 asked for a level named none: the designer filled the destination and spawn-point fields in the wrong order, twenty-four years ago. The original ignores it. Now so does this.

And the story gates on the other 36 portals were being applied with one condition overriding the other, instead of both applying — and applied at all to portals that carry no story gate.

The part that wasn't the plan

The session started on one task: port the level-transition portal faithfully and write the proof. It ended somewhere else twice, because things in the repository turned out not to be true.

Found

Three mutation tests that never ran

The project proves its ports are faithful with oracles: headless programs that drive the ported C and diff it against the behaviour recovered from the original executable. Four of them carry a self-test that deliberately breaks the ported code and requires the oracle to notice. It is the check on the check.

Three of the four never executed the broken code. The mutated copy is written to a temporary directory and compiled in place of the real file — and from there, a quoted #include no longer resolves. Every mutant failed to build, and each harness counted the build failure as "the oracle rejected it".

One of them said so out loud, every run, and nobody read it closely:

SELFTEST ok: base update dispatch removed rejected (dumper failed to compile)

Two of the three back certified claims whose notes cite the mutation test as the evidence. The sensitivity those notes describe is real — every mutant is genuinely caught now that they run. It simply wasn't being verified. A mutant that fails to build is now a failure, not a pass.

Found

Seven objects that "would draw a box"

The asset catalogue's front page — the list you pick work off — reported seven object types with no resolved visual, including the tree, at 169 placements across 12 levels.

None of them draws a box. Booting all 35 levels gives all entities resolved 35 times over. The cause was one regular expression: a generated table had grown a fourth field the day before, the pattern stopped matching, the map parsed as zero rows, and every object whose artwork is a sprite fell through to "unresolved". The generator prints the row count in its own log — sprite_chunk_map: 0 — and carried on.

Found

A gate that could report a clean check it never performed

The spec checker compares 209 written class specifications against three independently generated sources. Every finding it can produce is a disagreement — so a source that parses empty makes it agree with everything, print OK: no spec disagrees, and exit successfully. It verified that its inputs existed. It never verified it could read them.

It now refuses. Proven by drifting a copy of the repository one input at a time:

control (no drift)                             exit 0
gam_schema: class-map heading renamed          exit 2
gam_schema: instances heading renamed          exit 2
gam_schema: property heading renamed           exit 2
classids: columns reflowed to single spaces    exit 2
entities.c: binding table gains a field        exit 2
specs: generated template FourCC row renamed   exit 2
specs: hand-written template Ctor row renamed  exit 2

Two more tools had the same shape and were fixed with it — including the one that generates the project's own coverage numbers, which would have produced a confident report saying zero.

What we still don't know

The project treats "we don't know" as a deliverable. Two things surfaced that can't be settled without the original executable, and both are now written down next to the code that depends on them.

Unresolved

The task lookup can't return the value the portal checks for

The recovered portal code asks the game's task table for a story value and branches on -1, logging "Task not found". But two other specifications decompiled that lookup and both say it returns 0 when the name is missing, never -1.

If they are right, the branch is dead code and an unmatched task reads as zero — which blocks the 36 story-gated portals instead of passing them through. That is the opposite outcome. No other recovered caller in the game distinguishes the two. It is a five-line function; reading its return settles both questions at once, and needs a machine with the binary on it.

Unresolved

Fifteen objects that draw a question mark

All fifteen bare sprite objects in the game author no artwork at all, so the original's fallback fires and binds an icon from the editor's own set — the canvas the artist named question, sitting among trigger, load, camera. A designer placed them and never finished them, and the engine drew a question mark over each one.

Whether the shipped game really showed editor placeholders to players is a judgement call, not a fact we can extract — and the size it drew them at is precisely the part still unrecovered. So the finding is recorded and the renderer is untouched.
