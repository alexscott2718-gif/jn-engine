None of it has been run against the actual Neutron.exe process yet — the machine that hosts the original game was unreachable while this was built (see Blockers below). Treat this as a design + scaffold writeup, not a confirmed working patch.

Someone asked whether jn-engine's recent camera-movement fixes (walking-camera follow, camera-record write) could be applied to the original retail game, not just jn-engine's own reimplementation. Short answer: not directly — jn-engine is a separate, from-scratch executable that reads the original's asset files, it doesn't share code with Neutron.exe. This page documents the follow-up: an actual runtime patch mechanism for the original binary, reusing this project's existing capture-proxy infrastructure.

Mechanism

Load order

Reuses the same trick as the existing capture proxy (instrument/proxy): a ddraw.dll placed next to the game's exe loads ahead of the system one. All 22 exports are plain forwarders to the renamed real ddraw — this shim never touches a DirectDraw call, it just needs to be loaded early.

Hook

hook_install.c: a generic x86 primitive that overwrites a live function's first 5 bytes with a near jmp (E9 rel32) to a replacement of matching signature/ABI. Full replacement, no call-through — consistent with how jn-engine already reimplements logic rather than wrapping the original.

Target

Hooks UpdateWalkingCameraB (00439900), the walking-camera record write jn-engine already ported and oracle-certified as camera_record_walkcam_write.

What M1 actually does when armed

With C:\camerapatch_enable present, the hook installs and logs the live camera record (DAT_00509a50) and the player's turn-rate input (this+0x6d4) every frame, throttled — then returns without doing the original work. This validates that the hook fires and that reading live game memory is safe. It also means arming it freezes walking-camera follow — it is a mechanism smoke test, not the fix. Don't enable it during normal play.
