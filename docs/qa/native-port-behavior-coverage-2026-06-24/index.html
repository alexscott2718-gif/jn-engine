Changelog · 2026-06-24 · branch native-port. Picks up where the N1–N5 changelog left off. With the structural waves done (the engine plays the levels), this past day's work was about breadth: giving the individual game objects their real behavior, wiring the campaign's story-progression machine, and making the browser build actually expose both.

Summary

After waves N1–N5 the engine had the skeleton — bases, enemies, pickups, vehicles, and the game-flow/menu layer — but most of the ~90 distinct object types placed in the levels were still inert props. This past day closed almost all of that gap, driven by a single instrument: the new resolution/usage-aware Asset Catalog, whose strict query (“authored in a level, but no native behavior”, ranked by reach) gave an objective worklist. Working down it took the count of used-in-level FourCCs with a native behavior from the low-30s to 90 of 93 — the last three are documented resolver/positioning gaps, not behavior gaps. On top of that breadth, two structural pieces landed: the SCENE sequencer (the campaign's story-progress state machine, with both of its writers) and the first C3DGoddard companion slice. Finally, the browser build got a Campaign toggle and a real keyboard-input fix so the story and the talk system are reachable on the web. Every step held the same gate: tools/audit_faithfulness.py at 0 findings across all 35 levels, and a WASM rebuild verified by tools/qa_web_verify.py (16 browser checks).

The instrument: a resolution/usage-aware Asset Catalog

tools/build_asset_catalog.py · the worklist behind everything below

Rather than guess what to port next, the catalog cross-references every FourCC's visual resolution (which mesh/sprite/canvas it draws) with its level usage (how many instances, in how many levels) and its native behavior (which vtable, if any). The behavior worklist is then a strict query — instances > 0 AND native_behavior IS NULL — ranked by instances × level_count so the highest-reach gaps come first. Each class is then read from its decompiled spec (docs/decomp/<Class>.md) and ported to match, not invented. The catalog is browsable at exentt.com/JN-assets/catalog.

The SCENE sequencer — the campaign's story machine DONE

task_loader.c store · game_flow.c accessors · behavior_ai_trigger.c + behavior_friend.c writers · docs/decomp/_scene_sequencer.md

SCENE is one tag in the CTaskList task-state table — the campaign's story-progress counter, seeded to 30 at New Game. It has no autonomous driver; it only moves when a story event writes it. Reverse-engineering recovered the two writers and they are now both ported:

1. Player triggers. C3DAITrigger::ApplyAITriggerStoryProgress is a hardcoded ObjectTag × current-SCENE → new-SCENE patch table (~25 beats) run when the player trips a story-trigger volume. 2. Friend talks. Each friend's talk-pulse re-reads SCENE and writes the next beat, collapsed into one shared table driven from a single entry point (the T key → nearest friend).

Two previously-deferred consumers are now freed by the live store: 3FOW/C3DFowl (per-level SCENE windows) and 3YCA/C3DYokCargo (LEV5 SCENE>489), plus 3HUM's clone reveal at SCENE==0x5a. Every gate treats “no task loaded” as “show”, so a direct --level / audit launch is unchanged — the gates only bite in a real campaign run.

Validated against the visible result: New Game → tripping teleportexplanation advanced SCENE 0x1e→0x23; talking to friends advanced their beats (Carl 0x32→0x3c, …); level4c fowlinv closed the fowl window (visible→hidden); SCENE=0x5a revealed Humphrey + 4 clones.

C3DGoddard — Jimmy's companion DONE

behavior_goddard.c · 3GOD (code-spawned) · docs/decomp/C3DGoddard.md

Goddard has no .gam rows — the original spawns him in code — so the native engine synthesizes one C3DGODDARD companion after level load, but only in a campaign run (or an explicit test probe) and only when the level data references him. He honors the documented disabled-level table (he stays hidden in level1c/1d/4a/6a/6/7/vr06), follows Jimmy at a short offset, and runs the first re-activated mechanic: the 3MEP metal-can beacon asks Goddard to fetch a can within range, after which he collects it and returns to follow.

The scripted-control tail then wired the C3DAITrigger branch that targets him: the ~30 3AIT rows with AITarget == C3DGODDARD (SITGODDARD, GOGODDARD, PUTGODDARD, …) now drive his mode — patrol an authored point chain, follow, or hold a scripted sit pose — so a cutscene that places or walks Goddard isn't instantly overridden by his follow loop.

New Game: GOGODDARD → Goddard walked GODDARDPAT1 → GODDARDPAT2; SITGODDARD → teleported to gstart and held; the 3MEP fetch/collect/return path was un-regressed.

The browser build — campaign + keyboard, made reachable LIVE

web/shell.html, gamestate.c, game_flow.c, input.c, behavior_player.c

All of the story work above was invisible in the browser, because campaign mode was only reachable from the command line and a real input bug silenced the talk key.

Campaign toggle. A new Campaign button (and a ?newgame=1 URL) begins the New Game task at runtime — campaign mode on, SCENE seeded — and swaps into level1b; toggling off returns to free-roam. So the story progression and the friend talk-rewards can now actually be played in-browser.

A real input bug, fixed: input_just_pressed() aliased SDL's live keyboard array, which the browser updates asynchronously between frames — so for any held key previous == current and the “just pressed” edge was never seen. Keyboard jump / throw / respawn / talk all silently did nothing in the browser (only held-key movement and the event-based B key worked). The input layer now keeps its own per-frame snapshot, so edge-triggered keys work in both the native and web builds. The T key (talk to the nearest friend) was also un-bound from a redundant turbo toggle (the Speed button keeps that), and now reports the nearest friend's distance so it's observable.
Also hardened the touch/mobile detection: it keyed only on (pointer: coarse), which false-positives on touchscreen laptops and got the page “stuck in mobile mode” (hiding the keyboard controls). It now requires a coarse primary pointer and no fine pointer, with a ?touch=0 / ?touch=1 override.

Verified against the live deployed build in headless Chromium: ?newgame=1 → Campaign: On at level1b; a real keydown fires [TALK] and does not toggle turbo; the Campaign button round-trips On/Off with the level swaps logged.
