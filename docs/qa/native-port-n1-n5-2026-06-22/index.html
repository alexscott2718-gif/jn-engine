Native Linux Port - Waves N1-N5 COMPLETE

Changelog · 2026-06-22 · branch native-port. The reverse-engineered behavioral specs for all 208 Neutron.exe gameplay classes now drive runtime behavior in the native C engine (jnengine) — not a separate game runtime. This log summarizes the five porting waves that took the engine from "renders the levels" to "plays them."

Summary

With the decomp spec campaign finished (208/208 classes at status=spec), the project pivoted to a native Linux port: turning those specs into live gameplay in the C engine. The work followed the inheritance DAG — bases first, then families, then leaves — so each wave builds on the last instead of re-copying logic. Five waves landed in sequence: the shared base-behavior framework (N1), enemies/AI (N2), player combat + pickups (N3), vehicles (N4), and the game-flow / level-controller layer (N5). Every wave was gated the same way: JN_SCREENSHOT spot checks, a full tools/audit_faithfulness.py sweep that must stay at 0 findings across all 35 levels, and a WASM rebuild verified by tools/qa_web_verify.py (16 browser checks) before deploy. The browser build at exentt.com/jn-engine is the live result.

Wave N1 — Base behavior framework DONE

unblocks every later wave · C3DObject / C3DAnimated / C3DFlyingObject / C3DAI

The 208 classes are an inheritance DAG, so the shared bases were ported once as reusable native modules rather than copied per leaf. behavior_base.c gives every animated object the same lifecycle prologue (level-visibility gates, InitiallyVisible, per-entity HasCollision/trigger flags, anim advance). A movement_base helper plus a C3DFlyingObject wrapper extract the shared movement integrator so vehicles and AI can reuse it. behavior_ai.c exposes idle/seek/patrol primitives.

Proof the base is real: Carl's vt_walker was re-pointed onto the new behavior_ai patrol primitive instead of carrying its own waypoint loop — and still patrols correctly, with no visual regression.

audit_faithfulness.py -> 0 findings

Wave N2 — Enemies / AI DONE

C3DYokian family: 3SOL soldier, 3GUA guard, 3SPY spy · shared PROJ

The first enemies that react to the player. behavior_enemy.c ports the Yokian humanoids as a faithful subset of the C3DAI seek/scan/attack machine: they acquire the player when inside the authored VisibleRange + FOV cone, chase via the N1 seek primitive, and melee-strike on a cooldown in contact range (soldiers are melee in the decompiled body, so they spawn no projectile). The new behavior_projectile.c module is the shared, team-tagged spawn → integrate → world_query_segment wall test → AABB-overlap damage path — used by enemies and the player. Health lives in gamestate.c; enemy knockout uses an Entity.hp + a brief KO dwell.

Validated on level6: a soldier in yoksol's view cone walked from z≈−3475 to −3742 into attack range and struck the player (health 100→70); a thrown baseball logged the defeat and removed it.

Wave N3 — Player combat + pickups DONE

C3DBalloon (3BAL, 60 real instances) · the pickups family

Now the world reacts to the player's combat. A balloon rests until Jimmy's touch releases it (it drifts upward); a thrown baseball pops it for score using the decomp's distance-bonus formula (10 resting / 200 released base). The baseball is the shared PROJ_TEAM_PLAYER projectile from N2. The F throw is now gated behind actually carrying the baseball — faithful to C3DBaseballPickup's inventory flag — granted by collecting a 3PIC that awards PIC_NUMBER==6 or by the new behavior_pickup.c ability pickups (3BPU baseball, 3BUP bubble, 3HEL helmet, 3MEP score). Abilities are modelled as gamestate inventory tools.

On Level2, a granted baseball thrown at the nearest balloon scored; the N2 defeat path was confirmed un-regressed.

Wave N4 — Vehicles DONE

C3DRocketShip (3ROC, rideable) · C3DAISuv/C3DBus/C3DSailBoat (self-driving)

Vehicles split cleanly along their decomp base chains, both halves reusing N1 modules. The rocket — a C3DFlyingObject leaf placed in every level — is player-rideable: walk in and press E to board, fly with the move keys (forward/turn + SPACE up / CTRL down) over the N1 flying base, press E to dismount. While ridden it integrates its own position (not a physics entity, to avoid double gravity) and snaps the player onto it so the follow camera tracks the ride. vt_ai_vehicle drives the self-driving C3DAI traffic along its authored PatrolPoint chains via the same patrol primitive Carl uses.

Wave N5 — Game-flow / level controllers DONE

The biggest structural gap: main.c was a generic loop, not a port of the controller layer. Four pieces fill it.

CTaskList — the .tsk task-state loader

task_loader.c · docs/decomp/CTaskList.md

A C port of the .tsk deserializer that the game loads at level start: the start record (which .gam to load + spawn point) plus the initial mission entity-state table (NPCs, the SCENE sequencer, the REACTOR objective). Byte-exact with the reference Python parser. The proprietary .tsk binaries aren't distributed, so the loader falls back to a baked NewGame default derived from the committed parse.

Parses NewGame.tsk → level1b.gam, spawn (470.5965, 609.2417, −87.7631), 12-entity table including the non-default SCENE=30.

CJimmyGame — mission / lives / win-state + the level table

game_flow.c · collapses the 40 CLevel*Game / CLevelVR0N leaves

The per-level game-mode controller. InitGame seeds the mission layer exactly as the original (lives = 5, mission value = 100, mission active). The 40 zero-owned-method CLevel*Game leaves — which only bind a .gam — collapse into one data-driven level table instead of 40 near-identical hand-ports. Death now routes through the real lives/restart flow (a death spends a life and respawns; game-over resets the mission; manual R costs none) and the level-clear bridges to a real win-condition hook.

The RequiredLevel visibility gate is deliberately left env-driven: the original's progress counter runs into the ~550 range and its per-objective increments aren't ground-truthed yet, so feeding it a small campaign ordinal would wrongly hide gated objects. Mapping campaign progress → gate thresholds is a documented open question.
[JIMMYGAME] InitGame: lives=5 mission_value=100 active=1
[JIMMYGAME] begin task 'NewGame' -> level1b.gam (spawn 470.6,609.2,-87.8, 12 states)

C3DCutSceneCamera + C3DMultiCutSceneCamera — scripted camera timeline

behavior_cutscene.c · FourCC 3CAM / 3MCA

Each placed 3CAM registers a shot — its CameraTarget plus offset, distance clamp, zoom-ease rate and vertical look offset — and the runtime plays the level's shots in sequence (the 3MCA sequencer role), framing each named target. The cameras are invisible directors (no mesh, no collision).

level1a sequences its 3 shots (targets c3dgoddard, sw) to a rendered frame.
[CUTSCENE] play 3 shot(s)
[CUTSCENE] shot 2/3 target='c3dgoddard'

CMainMenu — front-end menu + level/task routing

menu.c · --menu

A keyboard-navigable title/level-select (Up/Down + Enter) over the loaded level as a backdrop. Items mirror the executable's level-file table: New Game → NewGame.tsk → level1b (turning on campaign mode), the 8 VR levels in their specced menu order, and Quit. Selections route through the existing level-swap machinery; gameplay freezes while the menu is up.

A level can now be entered from a menu, tracked to a win state, and transitioned — without per-level C hardcoding.
[MAINMENU] activate 'New Game' -> level1b (NewGame task)
[SWAP] loading assets/gam/level1b.gam
[JIMMYGAME] enter level 'level1b' (campaign idx 2, vr=0)

How the campaign layer stays out of the validators

The campaign entry, cutscenes and menu are gated behind --newgame / --menu / JN_CUTSCENE. A direct --level X launch — which is exactly how the faithfulness audit and the matched-camera validators drive the engine — keeps campaign mode off, so rendering is identical to before Wave N5. That is why every wave above could add gameplay while the audit held at 0 findings.

Verifying the behaviors

Two ways to confirm a class is doing the right thing — one in the browser, one static.

In-browser sandbox — ?sandbox=1

The browser build can't reach the JN_TEST_* env hooks and has no inventory UI yet, so combat and vehicles were undiscoverable. Adding ?sandbox=1 to the level URL reveals the rideable rocketship (the C3DRocketShip mesh, normally hidden) and grants the baseball so E (board / leave the rocket) and F (throw) work. A Controls panel under the level bar lists every binding. Default loads keep sandbox off, so the faithfulness audit is unaffected.

Try it: level1 with sandbox on — walk to the rocketship, press E to fly it, F to throw.
This also fixed a real contradiction: a prior QA ticket marked 3ROC invisible as a "scripted prop," but it is in fact the rideable vehicle (Wave N4). Sandbox reconciles the two so the vehicle is visible where it is boardable; the default path stays unchanged pending a dedicated visibility pass.

Static behavior-classification audit — tools/verify_behaviors.py

Every FourCC→behavior-vtable in entities.c is cross-checked against the decompiled class's base chain. Each gameplay role implies a structural invariant: a rideable vehicle must derive C3DFlyingObject, an AI-driven vehicle/enemy/walker must derive C3DAI, a pickup/camera its matching base. A misclassification — like confusing the rideable C3DRocketShip with the autonomous toy C3DRocket — now fails mechanically instead of only surfacing in play.
