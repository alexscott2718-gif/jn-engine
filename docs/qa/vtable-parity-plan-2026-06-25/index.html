Vtable Parity Plan native-port

Published 2026-06-25 · source docs: vtable_parity_plan.md and vtable_parity_handoff.md

This plan narrows the decomp work to the vtables that control visible game feel: camera, player movement, menus, inventory/tools, progression, triggers, animation, AI/pathing, and vehicles. The target is parity where manual generation would drift from the original game.

Success is not measured by raw vtable percentage. The useful metric is how many must-link parity systems are native-linked, faithfully ported, or still manually approximated.

Recommended Order

  1. Build docs/vtable_linkage_audit.md from the decomp ledger.
  2. Continue camera/cutscene linkage: finish 3CAM ViewFromCamera, actor facing, animation hooks, and PlayerControlled.
  3. Deepen C3DPlayer movement/camera slots that define tank-control feel.
  4. Audit and link menus/UI flow: CMainMenu, CMenuElement, C2DInGameMenu, pause/restart/input locks.
  5. Audit inventory/items/gadgets and progression/objectives.
  6. Then link trigger graph semantics, animation pose, AI/pathing, and vehicles.

First Implementation Slice

Audit

Create tools/build_vtable_parity_report.py and classify classes as linked, approximated, must-link, deferred, unused, or faithful-wontfix.

Cutscenes

Decode standalone 3CAM ViewFromCamera, then link target animations, facing, and player-control locks.

Validation

Use the web selector plus XP/noVNC or video timestamps as evidence. Avoid scene-specific overrides unless explicitly approved.
