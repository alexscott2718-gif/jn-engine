# Godot ↔ pipeline bridge — design sketch

*A concrete plan for running the **playable game** in Godot while keeping the
existing C/Python work as the **RE + asset foundry**. Draft for review.*

> **Status:** exploratory. Nothing here replaces the C engine's RE/replay/capture
> core — see [`PROJECT_HISTORY.md`](./PROJECT_HISTORY.md). This is about whether the
> *mechanics/feel* layer is better expressed in Godot, fed by what we already
> extract.

---

## 1. Principle — two tracks, one seam

```
   ┌─────────────────────────── C / Python (keep) ───────────────────────────┐
   │  ddraw/granny proxy → receiver → .omtc → replay   (FIDELITY / GROUND TRUTH)│
   │  OMT/GRN/GAM parsers → .glb export, sprite PNGs, static OMT texture reader │
   │  Level*.gam → C3DPlayer constants, entity tables                          │
   └───────────────────────────────┬──────────────────────────────────────────┘
                                    │  THE SEAM (data contract)
                       .glb meshes  │  + JSON level manifests
                       sprite PNGs   │  + physics.json + entity_registry
                                    ▼
   ┌─────────────────────────────── Godot (new) ──────────────────────────────┐
   │  LevelLoader (JSON → scene)  ·  CharacterBody3D player  ·  behaviors       │
   │  HUD/inventory  ·  follow cam  ·  triggers/doors/platforms  ·  exports     │
   └───────────────────────────────────────────────────────────────────────────┘
```

**The C side becomes a foundry.** It never moves into Godot. Godot never touches
D3D7/capture. They meet at a small, explicit **data contract**: `.glb` assets the
foundry already emits, plus a few JSON files we add. The C **replay** path stays as
the *oracle* you validate the Godot reconstruction against (same trick as
`native_vs_capture_8881` — diff a Godot frame against the captured reference).

Everything below is additive. If the Godot track doesn't pan out, you've lost a
weekend, not the engine.

## 2. The seam — data contracts

Three artifacts, all generated by **new `tools/export_godot_*` scripts that reuse the
existing parsers** (`gam_parser.py`, `omt_parser.py`, the `entity_visual` tables,
`player_physics` constant extraction). Godot consumes them; no Godot-specific logic
leaks back into the foundry.

### 2a. `levels/<name>.json` — level manifest
Generated from `Level<name>.gam` + the OMT placement data.
```jsonc
{
  "name": "level1",
  "sky": "bluesky3",                       // → which sky scene/material
  "spawn": { "tag": "3JIM", "pos": [x,y,z], "start_point": "" },
  "physics": "physics/level1.json",        // C3DPlayer constants for this level
  "placements": [                          // static OMT geometry (the world)
    { "name": "labshak", "glb": "res://assets/omt/labshak.glb", "pos": [x,y,z], "rot": [0,ry,0] }
  ],
  "entities": [                            // gameplay objects (from .gam)
    { "type": "3DOR", "tag": "DOORPP1", "pos": [x,y,z], "rot": [..],
      "props": { "target_level": "level1c", "start_point": "FRONTDOOR", "activate_target": "BTN1" } }
  ]
}
```
This is just the C `World` (entities + `WorldPlacement[]`) serialized — you already
build it in `gam_load` + `placements_load`. A `tools/export_godot_level.py` walks the
same data and writes JSON instead of populating C structs.

### 2b. `physics/<level>.json` — movement constants
Straight dump of the `C3DPlayer` block `player_physics.c` already parses
(MaxSpeed/Accel/Decel/UpRate/…). Godot's controller reads these as tuning, so feel is
**data-driven from the original**, not re-guessed.

### 2c. `entity_registry.json` (or a Godot `Resource`) — FourCC → scene/mesh
The Godot mirror of `src/game/entity_visual.c`'s tiers:
```jsonc
{
  "tag":  { "3PIC/hydrant": "res://entities/props/firehydrant.tscn" },
  "type": { "3JIM": "res://entities/player.tscn",
            "3DOR": "res://entities/door.tscn",
            "3PIC": "res://entities/pickup.tscn",
            "3TRE": "res://entities/tree_billboard.tscn" },
  "invisible": ["STRT","TRIG","LOAD","..."],   // markers — no visual
  "grn": { "gemred": "res://assets/grn/gemred.glb" }
}
```
Generated from the `TAG_TABLE` / `TYPE_TABLE` / `GRN_ASSET_TABLE` arrays so it stays
in lockstep with the C resolver.

**Assets are the easy part:** `.glb` is Godot's native import format, and OMT→glb /
GRN→glb already bake the breakthrough-correct canvas textures. They drop in as-is.

## 3. Component mapping (what ports to what)

| C engine (`src/game`, `src/engine`) | Godot |
|---|---|
| `World` + `WorldPlacement[]` | a level scene built at runtime by `LevelLoader.gd` from `levels/<name>.json` |
| static OMT placements (`.glb`) | `MeshInstance3D` (glTF import) |
| `3JIM` + `player_physics.c` (C3DPlayer consts) | `CharacterBody3D` (`player.tscn`) with `@export` tuning from `physics/<level>.json` |
| follow cam (tank-turn) | `SpringArm3D` + `Camera3D` rig |
| `behaviors/behavior_door.c` | `door.gd` on `door.tscn` (animate open/close) |
| `behaviors/behavior_button.c` → door | `Area3D` + signal to the linked door (by `activate_target` group) |
| `behaviors/behavior_movplat / plat` | `AnimationPlayer` or `Tween` path |
| `behaviors/behavior_checkpoint` | `Area3D` → `GameState.set_checkpoint()` |
| `behaviors/behavior_item` (3PIC/3GEM) | `Area3D` pickup → `GameState.collect()` |
| `behaviors/behavior_load` (LOAD trigger) | `Area3D` → `LevelLoader.swap(target_level, start_point)` |
| `behaviors/behavior_trig` | `Area3D` + signal |
| `hud.c` | `CanvasLayer` + `Control` (`hud.tscn`) |
| `gamestate.c` (items/tools/level swap) | `GameState` autoload (singleton) |
| `entity_visual_resolve()` | `EntityRegistry.gd` reading `entity_registry.json` |
| tree billboards / `2D_Trees` color-key | Godot `Sprite3D` (billboard) or alpha-scissor `StandardMaterial3D` |
| sky `bluesky3` cloud dome | `WorldEnvironment` sky or a rotating dome mesh |

Behaviors are tiny — most are 20–60 lines of C; their GDScript equivalents are
shorter because the scene tree + signals do the wiring.

## 4. The #1 risk — coordinate & scale reconciliation

The C engine has hard-won conventions: OMT exports localize geometry and the loader
maps **Max Y → GL −Z**, so native Level 1 draws placements at `(x, 0, −z)`; units are
large (thousands), camera `near=20 far=28000`.

Godot is Y-up, right-handed, −Z forward (like GL), and imports glTF in glТF space.
**Before any gameplay work, lock the transform** with a one-mesh spike: import one
`.glb`, place it at its OMT `pos`, drop the player next to it, and confirm
orientation/handedness/scale by eye against the C engine and the capture. Pin the
resulting `placement → Transform3D` rule once; everything else depends on it. Expect
to need a single consistent axis flip and possibly a world scale factor (e.g. 0.01)
to keep physics/camera numbers sane.

This is exactly the kind of thing the **C replay oracle** is good for: render the same
camera in Godot and diff against the captured frame.

## 5. Godot-side structure

```
godot/
├── project.godot
├── autoload/
│   ├── GameState.gd          # items, tools, checkpoint, level-swap request
│   └── EntityRegistry.gd     # FourCC(+tag) → PackedScene/mesh (from json)
├── core/
│   ├── LevelLoader.gd        # levels/<name>.json → scene tree; handles swaps
│   └── CoordSpace.gd         # the locked placement→Transform3D rule (§4)
├── entities/
│   ├── player.tscn + player.gd        # CharacterBody3D + C3DPlayer tuning
│   ├── door.tscn, pickup.tscn, button.tscn, platform.tscn, ...
│   └── tree_billboard.tscn
├── ui/ hud.tscn + hud.gd
├── camera/ follow_cam.tscn
└── assets/                   # symlink or import of the foundry's glb/sprite output
```
- **GDScript** for gameplay (fast iteration; the whole point). C# is available if you
  prefer typed code, but GDScript is the lower-friction choice for contributors.
- The foundry's `assets/glb/**` and `assets/parsed/sprites/**` feed `godot/assets/`
  (Godot import on first open). Keep `.godot/` (import cache) gitignored.

## 6. Phased plan (each phase gated against the C oracle)

- **Phase 0 — spike (½ day):** import `level1` glbs into one Godot scene, add a
  `CharacterBody3D` with Level1.gam constants, walk around. *Goal: validate
  coords/scale/feel (§4).* This is the go/no-go.
- **Phase 1 — data contract:** write `tools/export_godot_level.py` +
  `export_godot_physics.py` (+ registry). `LevelLoader.gd` builds the static world +
  spawn from JSON. *Gate: Godot level1 geometry matches the C engine's layout.*
- **Phase 2 — player + camera + registry:** `player.tscn` tuned from `physics.json`;
  follow cam; `EntityRegistry` places visible entities. *Gate: "feel" pass vs the
  data-driven C movement.*
- **Phase 3 — gameplay systems:** doors, buttons→doors, moving platforms,
  checkpoints, items/inventory, HUD, `LOAD` level transitions. *Gate: a full level1
  traversal works (the JNvsJN playthrough layer, re-expressed).*
- **Phase 4 — parity & polish:** sky, tree billboards, sprites, alpha cutout;
  desktop export first, then weigh web export. *Gate: side-by-side vs capture.*

The C engine stays the reference throughout; Godot is validated against it, not the
other way around.

---

## 7. What explicitly stays in the C/Python foundry
The proxy + receiver + `.omtc` capture, the D3D7→GL **replay** (fidelity oracle), all
OMT/GRN/GAM **parsing + glb export**, sprite extraction, and the **static OMT texture
reader**. These produce the seam artifacts. Godot is a *consumer* of the foundry,
never a participant in the RE.

---

## 8. Trade-offs to decide before committing
- **Web export.** Godot 4 HTML5 is ~30–40 MB + threading caveats vs the lean
  Emscripten bundle. Options: keep the C WASM demo as the light/faithful web build and
  ship Godot to **desktop first**; or accept the heavier web export for the full game.
- **Dual maintenance.** Acceptable *only* with the strict split above (foundry = RE,
  Godot = game). Don't let gameplay logic creep back into C.
- **Repo layout.** Start as a `godot/` subdir here (shares the pipeline, single source
  of truth). Split to a sibling repo later if it grows its own life — same call as the
  JNvsJN-vs-own-repo question.
- **Engine-as-artifact vs game-as-artifact.** If the clean-room engine *is* the deliverable
  (decomp ethos), Godot dilutes it. If a living, moddable, contributor-friendly Retroville
  is the goal, Godot is the accelerator. This is the real decider — see §1.

## 9. First concrete step
`tools/export_godot_level.py level1` → `godot/levels/level1.json` (reusing
`gam_parser` + placement data), then the Phase-0 spike. If walking around feels right
in an afternoon, that's your answer; if the coordinate/scale reconciliation fights
back, you've learned it cheaply.
